# Device compatibility and limits

The standard hardware is an unmodified Waveshare RP2350-USB-A. Connect one input device directly to USB-A. USB-C provides the configuration/output connection. Alternate RP2350 boards require the changes in the [GPIO guide](gpio-assignment.md) and their own hardware checks.

Unsupported scope includes USB hubs, Bluetooth, Low Speed/High Speed devices, HID array input interpretation, headset audio, Xbox-console authentication, and arbitrary vendor-specific initialization.

Resource limits are four HID interfaces, eight IN endpoints, 64-byte input packets, 256 decoded fields, 1,024-byte configuration descriptors, and 2,048-byte HID report descriptors. Inputs exceeding descriptor bounds are rejected instead of silently truncated.

## Low Speed and the unmodified board

The retro freak standard controller (`1345:1030`) enumerates on a PC as a Low Speed HID joystick with two 8-bit absolute axes, ten buttons, and an 8-byte interrupt input endpoint. Its captured descriptors are accepted by the existing HID parser, but that does not establish USB communication through this bridge.

The standard board retains the fixed 1.5 kohm D+ pull-up R13 shown in the [manufacturer schematic](https://files.waveshare.com/wiki/RP2350-USB-A/RP2350-USB-A.pdf). With this Low Speed controller attached, the measured idle state has both D+ and D- high (SE1), instead of D+ low / D- high. A local Low Speed prototype sent valid SETUP and DATA packets at 1.5 Mbit/s, but the controller did not acknowledge them. Selecting Low Speed in firmware does not remove the fixed pull-up or correct the external idle state. The [manufacturer FAQ](https://www.waveshare.com/wiki/RP2350-USB-A) also discusses removing R13 for PIO-USB host hot-plug detection; it does not establish operation of this particular controller after that change.

The project retains its unmodified-board requirement. Low Speed support has therefore **not** been added to the product. Firmware and product sources were restored to 0.20.16 after this investigation; existing Full Speed controllers are not automatically retried at Low Speed. Removing R13 or using another board would require separate physical validation and is outside the current supported setup.

## Controller-specific behavior

M30 wired input can expose different USB identities. The Switch-compatible path recognizes `057E:2009`, performs its USB handshake and report-mode initialization, and decodes report `0x30`. A controller power reconnection may be needed after resetting only the bridge. The observed identity transition does not establish the controller's internal mode-selection rule.

The Xbox 360-format backend accepts the corresponding interface class/subclass/protocol and packet format. Its decoded fields come from a fixed internal schema, not an actual HID report descriptor. The Switch-compatible backend likewise supplies an internal schema. Profile matching includes the relevant descriptor fingerprint so different input modes can have different profiles.

The observed Cyber Stick report has 13 declared buttons, a hat, and four unsigned 8-bit axes. In the checked analog operation, X/Y were the stick and Rz was the throttle; Z and some declared controls remained unchanged. Calibrate the actual unit rather than copying another unit's neutral values. DIGITAL mode and game-specific behavior need separate validation.

The mouse path selects relative X/Y and relative wheel input. For the EGRET controller, wheel movement is interpreted as paddle movement on the profile-selected X (horizontal) or Y (vertical) axis. The default is X; Y selection requires firmware 0.20.2 or later. Absolute axes are not automatically used as relative mouse input. An enabled matching profile is required. Firmware 0.20.16 supports independent trackball D-pad conversion and paddle X=left/right or Y=up/down conversion. In the original click modes, combined output adds D-pad clicks while normal pointer movement continues for both enabled sources. Physical D-pad inputs and direction assignments are not required. The device-wide persistent threshold defaults to 64 after separate hidden cursor gain (initially 6.0× ball / 1.5× paddle), with signed accumulation and one click followed by complete accumulator clear. Physical trackball/paddle operation on 0.20.6 has confirmed simultaneous pointer and D-pad transfers to a Windows PC with all four direction assignments empty: 770 complete clicks and 3,415 mouse movements, with no recorded drops. D-pad response on Switch HOME was still reported absent with 0.20.6. The user also reproduced missed very short taps on an ordinary controller. Version 0.20.7 added minimum 30 ms pressed and released phases; PC measurements showed 31.000–31.001 ms for both, and the user subsequently confirmed direction operation. Version 0.20.8 introduced a saved shared duration initialized to 16 ms. The user subsequently confirmed operation at 16 ms and accepted it as the fix. Version 0.20.9 keeps that default and adds Mouse UDLR settings for threshold 1–256 pt and hold time 1–512 ms. Version 0.20.10 separates the released interval into Wait time (default 16 ms, range 1–512 ms) and retains Hold time for the pressed phase. Missing wait settings inherit the old hold value. Physical save/readback and reboot checks confirm independent persistence; the final storage comparison changes only the new 16-byte wait record. Version 0.20.11 changes newly initialized settings to 30 ms hold and 20 ms wait; valid saved values, including 16/16 ms, remain intact. No new physical motion-timing capture was made for these settings/default changes. Version 0.20.12 adds independent gamepad-output assignments for the four movement directions. Four Switch-output drop-downs default to their corresponding directions; Reset to defaults restores those assignments. Earlier zero mappings retain their original directional behavior. Mappings are device-wide and preserve the existing timing behavior. Host tests cover every target and physical-target priority, but there is no new physical controller/Switch trial for custom assignments. Version 0.20.13 separates these assignments into Trackball and Paddle tabs, with reset limited to the displayed tab and the old shared mapping inherited by both sources. Deterministic host tests cover source-specific output, queued source identity, migration and saving; there is no new physical controller/Switch trial for this split. Fast movement can exceed the four-click waiting queue and is counted as dropped direction events; pointer movement continues independently.

Virtual Rolling (0.20.14) replaces paddle-generated clicks with a selected analog stick's 12-position, 30° direction. Initial phase is up; stopped output is centered with phase and residual retained. Sensitivity, left/right stick and reversal are device-wide options. Existing settings default to Button clicks. Full combined output retains pointer movement. Deterministic checks cover the conversion and scheduling, but no new physical controller/Switch or game trial has been performed for Virtual Rolling. The cited mechanical references establish a 30° detent basis, not this paddle's physical counts per revolution or speed; see [operation and sources](configurator-guide.md#virtual-rolling).

Trackball Hold (0.20.15) evaluates each valid report independently, with a dedicated raw threshold 1–127 (default 1). It releases on zero, subthreshold movement or reversal of the old direction, and supports independent X/Y holds through the existing output mappings. The original trackball click mode is shown as Virtual Cursor in the current configurator (formerly Virtual Rolling); paddle modes are unchanged. An idle safeguard releases after max(20 ms, two input polling intervals) without a valid trackball report. Host tests cover thresholds, queue transitions, report separation and migration. No physical controller/Switch or game trial has been performed for Hold; see [Hold setup](configurator-guide.md#trackball-hold).

Version 0.20.16 adds a shared Paddle Virtual Rolling rotation step: 5°, 10°, 15°, 20°, 30°, 40°, 45°, 60° or 90°, with 30° as the upgrade/default value. All choices divide 360°; 5° has 72 positions, 30° has 12, and 90° has four cardinal directions. Changing step aligns the retained angle to the nearest new position and clears the residual on the next nonzero input. Existing modes, gains, maps and stop/resume behavior remain intact. Deterministic host tests cover every step, full turns, unchanged default vectors, cardinal outputs and RSD1 migration. Actual game compatibility and the physical paddle's counts per revolution remain unverified for this change; use matching normal firmware for stick output.

## Output and game behavior

Gamepad output retains the project's verified Switch-compatible descriptor path. Mouse-only output uses development identity `CAFE:4004`; this is not a production USB identity allocation. Combined mode exposes separate mouse and gamepad HID interfaces.

Mouse Report Protocol supports signed 16-bit movement; Boot Protocol supports signed 8-bit movement. Larger movement is split while retaining residual displacement. Movement and click queues are independent, but overload is not guaranteed lossless.

Mouse movement with Minus, Plus, and HOME has been verified on Switch 2. Combined full-gamepad behavior also depends on how a game assigns player 1/player 2 and accepts devices. USB delivery alone does not prove game adoption.

**Combat School movement speed remains unresolved.** Input at 1 ms and trackball gain 64 improved the result but did not reach the tested gaming mouse's full-power response. Paddle input was also insufficient, and small back-and-forth trackball movements behaved differently from sustained movement. Current software does not claim to resolve that game-specific behavior.

The configurator's live axis list has been checked using deterministic input notifications and rendered layouts. Physical calibration and in-game response still need checking for each actual analog controller. See [current verification](verification.md).

## Identifying the connected host console

Investigation dated 2026-11-09, firmware 0.22.0: the normal firmware does not identify the downstream console as Switch or Polymega. Standard USB HID requests let the host inspect and configure the peripheral; they do not expose a host-console model identifier for this device to query. The bridge's VID/PID describes the bridge's emulated controller, not the host console. [USB-IF HID specification, sections 6–7](https://www.usb.org/sites/default/files/documents/hid1_11.pdf)

The normal output in apps/egret_switch/main.c uses the PowerA-compatible HID identity and report path in lib/controller_device/switch_wired.c. It does not activate the Pro Controller command handler in switch_protocols.c. Consequently, an absent Pro Controller handshake cannot distinguish the two consoles on this output path.

For Polymega Base Unit, the manufacturer describes a proprietary Linux-based operating system. This is not evidence of a unique USB request sequence, nor does it identify the exact USB/HID driver used by a particular firmware version. Moreover, Linux's own hid-nintendo driver sends Pro Controller handshake, baud-rate and timeout commands, so observing those commands alone would not prove a Nintendo console. These findings also do not establish whether ControllerBridge's current USB identity is accepted by Polymega. [Polymega FAQ](https://polymega.com/pages/frequently-asked-questions), [Linux hid-nintendo source](https://github.com/torvalds/linux/blob/master/drivers/hid/hid-nintendo.c)

An empirical classifier may be possible if captures from the actual consoles show stable differences in descriptor request order and lengths, string requests, SET_IDLE/SET_PROTOCOL, or report requests. No Polymega-specific capture or reliable public signature was found in this investigation. The classifier would need positive signatures for each supported host, an Unknown result, and validation across reconnects, startup/resume and all three bridge output modes; absence of one signature must not mean the other console. USB polling intervals alone are insufficient because the bridge advertises its requested interval and multiple hosts can use the same rate.

The native driver already exposes observe_setup/observe_event hooks. A diagnostic capture could reuse them without changing the output identity or input reports. The existing local RAM trace stops at the next bus reset and is not sufficient unchanged for capturing the subsequent initial enumeration; capture start/stop and retrieval across host reconnection must be adapted first. Until comparative hardware evidence is available, explicit target selection is the dependable approach for behavior that must differ between consoles. This investigation adds no detector, probe traffic or firmware memory usage.

## XInput output on Windows

In X mode, Windows uses its installed Xbox 360 driver for game input. Since 0.25.1, Gamepad output uses 045E:028E and the reference four-interface configuration without a configuration HID. The matching configurator uses Windows' standard USB hub driver to access settings and firmware updates while the Xbox driver remains attached. Xbox-console authentication, headset audio and rumble forwarding are not implemented. See [X output and configuration access](xinput-output.md).
