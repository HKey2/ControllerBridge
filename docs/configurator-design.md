# Configuration and storage design

This describes the current ControllerBridge configurator 0.20.16 and firmware 0.20.16. It is an implementation reference, not a release history. See the [user guide](configurator-guide.md) for normal operations.

## Architecture and capabilities

Core 1 runs the PIO input host. Core 0 handles mapping, output, configuration, and the status LED. Input uses the pinned Pico-PIO-USB transport; the native RP2350 USB device path is implemented by this project. TinyUSB is used only by the separate CDC diagnostic target.

The GUI is a self-contained Windows x64 WinForms application built with the existing .NET 9 SDK. It edits the board's 16 slots directly. It requires 848-byte profiles, 16 slots, and capability bit 12 for the current settings format; saving enabled shift settings additionally requires bit 14, and saving a Y-axis paddle setting requires bit 15. Gain above 64 requires bit 16; either movement-conversion preference requires bit 17. These checks run before profile/bank uploads. The explicit profile-size field is authoritative. Single-slot writes are read back with their identity before command 46 applies the effective output.

The GUI uses per-monitor V2 DPI awareness. Every form holds layout suspended from `Ui.Form` until its constructor has populated the entire 96-DPI control tree. Disposing the returned layout scope enables the initial scaling pass. Consuming this baseline before adding the controls can leave their dimensions unscaled, then shrink them again when a high-system-DPI process opens on a lower-DPI monitor. Mapping editors use the same baseline and stay parented while hidden; the registration wizard also retains all three pages so they receive font and DPI changes. Single-column layouts explicitly follow the available width, while mapping-cell dimensions retain their logical size. Owner-drawn secondary text derives its size from the scaled control font.

On show and after a DPI change, windows fit within the current monitor's working area. Content retains its logical minimum size with scrollbars when necessary. The main window starts at 1290×1100 logical pixels and permits a 1290×700 content minimum, with the mapping area scrolling independently. The DPI regression runner is `tools/check-gui-dpi.ps1`; it exercises synthetic startup DPI and native DPI-change notifications without changing Windows settings or opening a USB device. See [verification](verification.md) for the tested conditions and limits.

The input path supports one directly connected Full Speed device, up to four HID interfaces, eight IN endpoints, 64-byte input packets, and 256 observed fields. Variable HID inputs, report IDs, absolute axes, and four/eight-direction hats are supported. Relative movement uses the dedicated mouse path. See [compatibility](compatibility.md) for tested and untested devices.

## Paddle axis semantics

Mouse flags at profile offset 480 use bit 5 for the paddle destination: zero means X and one means Y. Bits 6–7 enable trackball and paddle conversion respectively. `MouseProfileSettings.PaddleAxis` is the X/Y enum, serialized as 0/1 in JSON; an omitted property defaults to X. No version or size bump is needed: profiles remain v6/848 bytes, banks v6/13,908 bytes, and individual JSON exports v3. Older saved X settings retain their exact wire bytes.

The mixer applies paddle gain and its own reversal to the wheel delta, then adds it to the selected axis before per-axis fractional rounding. Trackball reversal is applied only to trackball movement. The runtime resets fractional state when it reloads a profile. No additional per-profile storage or runtime buffers are allocated. Command 37 reports the same eight-byte settings block; capability bit 15 announces support. GUI single-profile and bank writes, and CLI profile edits, reject a Y setting on older firmware before sending write commands. Older firmware/GUI cannot load a Y profile; save all paddle settings as X before downgrading.

## Profile wire format

The canonical profile is version 6, 848 bytes, little endian. The C definitions and C# codec validate fixed sizes and field ranges. The original 488-byte prefix retains its fields; version-5 profiles migrate by changing the version and appending disabled shift settings. Versions 1–4 remain unsupported. Normal USB profile transfers use only the current 848-byte format; legacy conversion applies to stored banks and JSON imports.

| Offset | Bytes | Field |
|---:|---:|---|
| 0 | 2 | Profile version |
| 2 | 2 | Flags: enabled=1, descriptor match=2, revision match=4, custom LED RGB=8 |
| 4 / 6 / 8 | 2 each | VID / PID / bcdDevice |
| 10 | 1 | Input interval in ms; zero uses the descriptor |
| 11 | 1 | Four 2-bit axis modes: disabled=0, analog=1, digital pair=2 |
| 12 | 4 | Input descriptor fingerprint |
| 16 | 48 | NUL-terminated UTF-8 name, at most 47 data bytes |
| 64 | 288 | 18 digital bindings, 16 bytes each |
| 352 | 128 | Four axis bindings, 32 bytes each |
| 480 | 1 | Trackball enabled=1, paddle enabled=2, invert X=4, invert Y=8, invert paddle=16, paddle Y=32 (clear means X), trackball D-pad=64, paddle direction conversion=128 |
| 481 | 1 | Low byte of trackball gain multiplied by 10 |
| 482 | 1 | Paddle gain multiplied by 10, range 10-100 |
| 483 | 1 | High byte of trackball gain; combined range 10-2560 |
| 484 | 1 | Bits 0-1: gamepad=0, mouse=1, combined=2; bit 2: controller-button behavior |
| 485 / 486 / 487 | 1 each | LED red / green / blue (RGB888), each 0-255 |
| 488 | 4 | Shift override mask, bits 0–17 in digital output order |
| 492 | 1 | Modifier count: 0 disables shift; 1–4 require all keys held |
| 493 | 3 | Reserved, zero |
| 496 | 64 | Four physical modifier bindings, 16 bytes each; unused entries disabled |
| 560 | 288 | 18 shifted digital bindings, 16 bytes each |

Flag bit 3 (`UP_LED_CUSTOM`) enables the three LED bytes. With the bit clear all three bytes must be zero, and ready output is the existing R=0/G=0/B=1. With the bit set, bytes are output exactly; all-zero custom RGB means off. Matching still uses only flag bits 1 and 2 (values 2 and 4), so color does not change controller grouping, profile selection, or shortcuts. The three RGB bytes retain their existing offsets. The profile flag field still has 12 unused bits. The appended shift block adds 360 bytes per profile; bank-copy spare space is now 2,460 bytes.

Migration preserves version-5 LED values, including the zero default in 0.16.x/0.17.x records. Missing LED properties in old JSON decode as zero. The normal GUI checks for exact matching firmware before editing the bank; older configurators cannot edit the expanded version-6 bank.

Valid output bytes are 0, 1, 2, 4, 5, and 6. The controller-button preference is retained even while another tab is selected. Every accepted profile includes this field. Whole-bank operations preserve original profile bytes rather than rewriting unrelated slots.

Digital binding fields are interface (1), report ID (1), bit offset (2), bit width (1), mode (1), flags (1), rapid rate (1), lower bound (4), and upper bound (4). Flags are signed=1 and report-ID-present=2. Mode 0 is disabled, 1 compares a range, and 2-5 represent hat Up/Right/Down/Left. Rapid fire is zero (Off) or 1–60 cycles per second; unassigned bindings and analog digital pairs require zero. The GUI starting rate for an Off output is 20, without rewriting stored rates or enabling outputs automatically. Firmware capabilities advertise bounds 1 and 60 in bytes 48–49. This range expansion changes no wire offsets or profile/bank versions; older firmware still rejects rates outside 2–30.

Digital output order is Y, B, A, X, L, R, ZL, ZR, Minus, Plus, left-stick press, right-stick press, HOME, Capture, Up, Right, Down, Left.

An analog binding contains interface (1), report ID (1), bit offset (2), bit width (1), flags (1), reserved (2), minimum (4), center (4), maximum (4), dead-zone percentage (2), and reserved (10). Flag bit 2 enables inversion. A digital-pair axis instead contains negative and positive 16-byte bindings; both held gives center. Axis order is LX, LY, RX, RY. Values received on separate interfaces/report IDs are retained and combined. Bit offsets exclude the report-ID byte.

## Profile bank and Flash

The version-6 bank is 13,908 bytes: 16-byte bank header, 16 x 848-byte profiles, 256 bytes of IDs, 4 bytes of preferred selections, and 64 bytes of shortcuts. IDs use the byte order of .NET `Guid.ToByteArray()` / `new Guid(bytes)`. The 16-byte outer CRC header makes a stored copy 13,924 bytes, leaving 2,460 bytes in each 16 KiB bank area.

| Storage slot | Offset with 2 MiB Flash | Size | Purpose |
|---:|---:|---:|---|
| 4 | `0x1F4000` | 16,384 | Bank A; first version-6 commit after migration |
| 5 | `0x1F8000` | 16,384 | Bank B; overlaps both old 8 KiB bank copies |
| Unused | `0x1FC000` | 8,192 | Reserved; no reads or writes |
| 0 | `0x1FE000` | 4,096 | Common settings, unchanged |
| 1 | `0x1FF000` | 4,096 | Saved measurement, unchanged |

The Flash header retains magic `CBST` (`0x54534243`), storage version 1, payload length, and CRC-32. The newest valid version-6 bank wins. If none exists, startup reads the version-5 copies at `0x1F8000` and `0x1FA000`, checks CRC and structure, selects the newest valid generation, and expands all profiles in RAM while preserving IDs, selections and shortcuts. Loading never writes Flash. The first migrated save writes/verifies Bank A before old banks can be overwritten; a later save can use Bank B only after a valid new copy exists. Tests simulate interrupted first and subsequent commits.

If neither a current bank nor a valid version-5 bank exists, startup creates 16 unused slots in RAM with generation zero and `persisted=false`. Pre-0.16.0 storage identities remain rejected. No EGRET preset is created. Common settings and saved measurements keep their existing addresses and identity.

Normal updates write and verify the inactive copy before adopting it. The total reserved tail is 48 KiB, and writes check for overlap with code. The unused 8 KiB remains reserved. The application UF2 validator rejects payload addresses at or above `0x101F4000` on the standard 2 MiB board.

Whole-slot JSON uses `ControllerBridge.Slots`, JSON version 3, UTC creation time, Base64 bank bytes, and SHA-256. Individual JSON uses `ControllerBridge.Profile`, JSON version 3, and excludes bank metadata. Version-2 exports with version-5 data are validated and migrated with shift disabled. JSON version 1 and binary profile versions 1–4 remain unsupported. Exports write a temporary file, read it back for verification, then replace the destination. Imports are limited to 256 KiB and validated before drafts change. Older firmware/configurators cannot read new records; retain a pre-upgrade backup for downgrade recovery.

## Button shift runtime

Each profile has one main button page and one shifted page; axes, identity, output mode, input interval and mouse settings are common. Each override bit replaces one output binding, including its rapid rate. A disabled override explicitly mutes that output. Unset bits inherit the main page. Active overrides suppress inherited button outputs driven by the same overlapping physical input, preventing a moved button from generating both its old and new output. Overlap compares interface, report ID, bit range, signed/report-ID flags and activation values; it is not based on button labels.

The mapper retains both pages' pressed states, raw modifiers, digital axis pairs and analog values across report IDs/interfaces. Modifier AND detection precedes output for the current report. On any modifier release the main page returns; modifier bindings remain consumed until all are released. Inputs already held are recomputed for the newly active page. Profile activation seeds all cached field values; detach clears state. Conflict masks are calculated at attach rather than by an all-pairs scan per report. Page edges reset rapid phases without changing the selected profile or writing Flash.

Modifier consumption includes a shared physical source used by a common axis. Otherwise the four axes keep their main-page behavior. Partially held multi-key chords can produce their main mappings before the chord first completes; single-key modifiers are consumed immediately. No tap/hold or chord timing window is implemented. Dedicated unmapped physical modifiers avoid pre-chord normal outputs.

Permanent profile shortcuts read the main physical bindings and are suppressed during modifier consumption. The profile/bank validators reject overlapping modifier/shortcut inputs, including individual edits and shortcut changes. No shifted page alters the stored active profile ID. See [button shift](button-shift.md) for the user workflow and examples.

## Feature transport

Feature data is 64 bytes; the Windows HID API prepends report ID zero for a 65-byte buffer. Bytes 0-3 are `UC2C` / `UC2R`, byte 4 is transport version 1, byte 5 is command, byte 6 is sequence, byte 7 is response status, and bytes 8-63 are payload. Offsets below are relative to payload. Integers are little endian.

Status values are 0 success, 1 malformed request, 2 measurement busy, 3 save failure, 4 generation conflict, and 5 rejected legacy setting operation. Slots are 0-15; 255 means no selected slot.

| Command | Operation |
|---:|---|
| 9 | Request BOOTSEL after a 250 ms response window |
| 20 | Capabilities (`UPG1`): profile size/count, active slot, fields, device identity, connection/bank generations, event cursor, input interval, host/protocol state, feature bits, rapid range, profile number/count, shortcut |
| 21 | Read a decoded input field and its current value |
| 22 | Read up to four input change events from a cursor |
| 23 | Read up to 56 bytes of a slot from a supplied offset |
| 24 | Begin slot staging: slot, CRC, expected generation, optional profile ID |
| 25 | Append up to 52 bytes to slot staging at an offset |
| 26 | Validate and save the complete staged slot; return generation |
| 29 | Read cached device/configuration descriptor fragments |
| 30 | Read the latest raw input packet, sequence, and receive timestamp |
| 31 | LED diagnostics (`LED1`) |
| 32 | Read slot ID, generation, and profile CRC consistently |
| 33 | Select a saved matching profile with an expected generation |
| 34 | BOOT sampling/switching diagnostics (`BTN1`) |
| 35 | Read or save the shortcut for all profiles matching the selected controller |
| 36 | Mouse output and queue diagnostics (`MSE1`) |
| 37 | Effective per-profile mouse settings (`MPR1`) |
| 38 | Active mouse protocol and wire format (`MWR1`) |
| 39 | Build-time fixed-motion probe settings (`MFP1`) |
| 40 | Bank info: `UPB1`, byte count, generation, CRC |
| 41 | Read up to 56 bank bytes using offset and expected generation |
| 42 | Begin bank staging using expected generation, CRC, and full length |
| 43 | Append up to 52 bank bytes using offset and length |
| 44 | Commit a complete valid bank and return generation/CRC |
| 45 | Abort bank staging |
| 46 | Apply the active profile's output after checking expected generation and slot; return `OUT1` and current/pending/reconnect state |
| 47 | Normal firmware identity (`CBV1`), version, and target board; see [firmware update](firmware-update.md) for the byte layout |
| 48 | Begin registration into an empty slot, guarded by the captured input attachment and identity |
| 49 | Read direction generation/ACK/drop counters (`DKY1`) |
| 51 | Read actual generated-direction timing (`DPT1`, 0.20.7+) |
| 52 | Read shared timings, source targets and both conversion modes (`UDS7`, 0.20.16) |
| 53 | Validate, save and apply shared timings, source targets and both conversion modes (`UDS7`, 0.20.16) |

The implementation is authoritative for byte-level command layouts: [`profile_runtime.c`](../lib/controller_bridge/profile_runtime.c), [`main.c`](../apps/egret_switch/main.c), [`HidBridge.cs`](../gui/ControllerBridge/HidBridge.cs), and [`controllerctl.py`](../tools/controllerctl.py).

Capability bits 0-12 represent rapid fire, IDs, on-board variants, shortcuts, immediate switching, mouse output, extended-profile/16-slot support (originally 488 bytes; read the explicit size field), combined output, combined full-gamepad buttons, extended trackball gain, 16-bit mouse output, whole-bank transfer, and per-profile output. Bit 13 (8192) adds guarded registration. Bit 14 (16384) adds button shift and the 848-byte profile. Bit 15 (32768) adds selectable paddle X/Y output. Bit 16 (65536) adds trackball gain through 256.0. Bit 17 (131072) adds movement-to-D-pad conversion. Bit 18 (262144) adds shared direction-settings commands 52/53. Bit 19 (524288) adds direction-output assignments and UDS3/schema 3. Bit 20 (1048576) adds independent trackball/paddle assignments and UDS4/schema 4. Bit 21 (2097152) adds Virtual Rolling and UDS5/schema 5. Bit 22 (4194304) adds Trackball Hold and UDS6/schema 6. Bit 23 (8388608) adds configurable rotation steps and UDS7/schema 7. The normal firmware advertises 16777215. Clients must check the relevant bits rather than infer support from names.

Command 48 keeps the first 26 bytes of command 24: slot at 0, profile CRC32 at 1, expected bank generation at 5, ID-present flag (must be 1) at 9, and 16-byte profile ID at 10. It adds expected input connection generation at 26, descriptor fingerprint at 30, VID/PID/revision at 34/36/38, and input protocol at 40. All multibyte integers are little endian. A dedicated command and capability prevent old firmware from silently ignoring the guard.

Registration requires a connected matching attachment and an empty saved destination. Commands 25 and 26 retain the guard until commit. Probing/disconnection invalidates the staged registration even when the same controller returns. Commit rechecks connection generation, destination, exact staged identity, descriptor matching, and that mapped sources exist before any Flash save. Conflicts return status 4; a Flash failure remains status 3. Ordinary command-24 profile editing still permits editing saved profiles while the input is absent. Guarded registration uses the current version-6 profile and validates modifier and overridden input sources as well as main mappings.

The 256-entry event ring stores field index, flags, value, and timestamp. GUI polling runs every 25 ms. Learning drains old events before taking its baseline and aborts on a connection generation change or an overrun. Captured input events do not trigger Flash writes.

The registration input log observes this same parsed-field stream before the learning-delivery gate, including baseline-drain events and the last received overrun event. It makes no additional USB requests. Initial snapshots have no device timestamp; event rows retain the original 32-bit microsecond timestamp without treating a wrap as negative elapsed time. The index is the zero-based firmware field index, independent of HID Usage/button numbering and output mapping indexes. Decimal values and width-masked hexadecimal values are recorded before GUI calibration or mapping. Identical USB reports from two physical controls cannot be distinguished, and unchanged fields are not a packet trace.

`InputLogBuffer` bounds PC history at 2,000 immutable rows with an eviction count. `InputLogForm` uses a virtual list and batches repainting at 100 ms; the existing learning path still receives every delivered change. `InputLogListView` explicitly enables the native double-buffer style. For pure appends, it preserves WinForms' managed item count while forwarding `LVM_SETITEMCOUNT` with `LVSICF_NOINVALIDATEALL | LVSICF_NOSCROLL`; offscreen appends do not repaint visible rows. Clearing or rotating the ring redraws item content, tracked by the buffer reset generation and eviction count. There is no unconditional whole-control invalidation on an ordinary update. Following only requests a scroll if the last row is outside the vertical viewport. Status text, including a retained notice, is composed before a single assignment, avoiding a temporary one-line layout on each two-line update. See Microsoft's [item-count flags](https://learn.microsoft.com/en-us/windows/win32/controls/lvm-setitemcount) and [native double-buffer style](https://learn.microsoft.com/en-us/windows/win32/controls/extended-list-view-styles).

Pausing the log does not pause polling or learning; resuming records an omission notice and a new snapshot. The log is a modeless sibling of the modal registration wizard, owned by the main form. Wizard closure finishes the log without reparenting windows during closing, so diagnostics remain available for export. All storage is on the PC; firmware buffers, persistent layouts, and board memory requirements are unchanged.

## Output scheduling and measurements

Output state values are 0 Gamepad, 1 Mouse, 65 combined mouse-button behavior, and 193 combined controller-button behavior. These differ from profile byte 484. Common configuration byte 7 retains its diagnostic protocol position; current output-mode changes must use profiles.

A layout change waits 250 ms after the response, disconnects USB-C, then reinitializes after another 250 ms. USB-A reception continues. Only the current button state initializes the new output; relative movement accumulated during disconnection is not replayed. Measurement starts after any output transition completes.

Mouse movement and click transitions use independent 64-entry queues. Report Protocol supports signed 16-bit movement and combines up to eight pending input movements; Boot Protocol uses signed 8-bit movement and combines up to two. Only acknowledged movement is consumed. Click transitions do not wait for queued movement to drain. Capacity overflow is counted rather than claimed to be lossless.

The current saved measurement payload is 3,784 bytes. Its `DUO1` extension separates mouse and gamepad counters, and `MBT1` records click transitions and the formats actually acknowledged. With the 16-byte header it occupies 3,800 of 4,096 bytes, leaving 296 bytes. Input-receive-to-output-ready/ACK statistics exclude the input controller's internal scan and the game's response. See [diagnostics](diagnostic-guide.md).

## GUI behavior

`ConnectionRead` reads command 47 before settings and owns the HID handle until the complete bank/input/output snapshot is ready. Unknown or different firmware returns a classified status without attempting to decode incompatible profiles. Background connection attempts have a separate `connecting` guard, so they do not toggle the main form's `working`/enabled state. Manual operations supersede pending attempts; late results after closure are disposed. A modal editor defers background discovery.

If no bridge HID is found, discovery enumerates present `GUID_DEVINTERFACE_USB_DEVICE` interfaces and resolves each USB parent and location path. Pico SDK CDC/reset (`2E8A:0009`) and RP2350 BOOT (`2E8A:000F`) parents become installation candidates. Composite child interfaces are not counted separately; unrelated USB devices and RP2040 BOOT (`2E8A:0003`) are excluded. Candidate ordering and case are normalized for stable notice keys. This is metadata enumeration only: it does not open the serial port or send reset commands. The factory board supplied for verification exposes product name `Pico` and `2E8A:0009`; this shared identity is not proof of a particular carrier board.

`FirmwareNoticeTracker` records each detected device/version notice until a disconnected state is observed. Factory/BOOT candidates and unreadable bridge firmware use `UnknownFirmware`, displayed as **Device unsupported**. No recognized board uses `NotDetected`, displayed as **Device not connected**, and never opens guidance. Cancelling the BOOT wait or declining confirmation suppresses repeat prompts during that connection; a later observed absence rearms guidance for reattachment. The updater is opened after releasing the connection guard and performs its own fresh version check. Its return reconnects with automatic guidance suppressed, preventing cancellation loops. Version matching is exact equality, with no upgrade/downgrade ordering.

The updater also records a single factory/BOOT candidate's USB location. Multiple candidates fail without selecting one. After the user follows the BOOT guide, the programming disk must be on the recorded port, just as for a normal versioned application. RP2350 USB/INFO_UF2 checks and the separate overwrite confirmation remain required. Manual recovery with no previously detectable target still allows a single validated RP2350 BOOT disk.

When the version is unavailable, `FirmwareWorkflow` enters `WaitingForBootsel` immediately, with no initial Yes/No prompt. `PrepareAsync(null, token)` polls for a validated BOOT disk every 250 ms until detection or cancellation; manual reconnection has no timeout. The dialog displays numbered physical steps and only **Cancel**, with Escape and window-close cancellation. Cancellation is checked after discovery as well as during polling so that cancelling at the detection boundary cannot open confirmation or start writing. After valid detection, `ConfirmOverwrite` opens the final Yes/No prompt, defaulting to No. Only Yes starts writing; `WriteAsync` revalidates the selected disk and USB identity after confirmation. A readable version mismatch retains its existing confirmation, automatic BOOT transition, and 30-second BOOT timeout.

`ControllerArrivalTracker` consumes one navigation per initialized input attachment. It checks saved and draft profiles with the normal matching rules. The destination is the first slot with no saved profile, enabled draft, or dirty flag. Navigation runs after the polling/connection guard is released and waits for clean drafts, an up-to-date bank/input snapshot, and no foreground/modal operation. It only selects a list row; no device command is sent. The no-space condition is persistent header text, not a modal prompt. Registration captures the original bridge object, bank generation, and input identity and rechecks them after waiting for polling; firmware command 48 supplies the commit guard.

Status labels change only when the complete displayed text changes. Input events all reach the learning logic, while the live label receives only the final value in each polling batch. Empty USB-A host retry counters do not rebind the editor. Layout containers, the main form, firmware dialog, and custom buttons use buffered painting. Repeated offline discovery retains status, selection, and drafts without repeated enable/disable changes, layout, invalidation, or rebinding.

Names are persisted with duplicate suffixes; the list does not derive changing numbers from slot order. The initial and minimum client area is 1290 x 1100 at 96 DPI (1306 x 1139 with the checked window frame). The profile pane is 400 pixels wide, with ellipsis for longer names. Analog sources use a live list with centered meters and multiple columns when needed. The live numeric label reserves the measured localized signed-32-bit width, so adjacent calibration buttons do not shift with its value. Documentation images use English; saved-profile images reflect the device bank described in the guide. The application retains both UI languages.

## Pointing-to-direction conversion (0.20.16)

Mouse flags now use all eight bits. `Mouse.TrackballToDpad` and `Mouse.PaddleToDpad` default to false in JSON that lacks them. Profile version 6/848 bytes, bank version 6/13,908 bytes and JSON version 3 are unchanged. The current codec rejects mouse-only output when an enabled source requests D-pad conversion; the GUI/CLI choose combined output instead. Off sources may retain their preferences.

`um_direction_keys` maintains three signed 32-bit sums in tenths. Input multiplication and addition use 64-bit temporaries; remaining sums are bounded below `threshold * 10`. The device-wide `udk_settings` cursor gains and profile inversion precede accumulation; saved profile pointer sensitivities do not affect direction sums. The 32-byte runtime structure holds a u32 threshold, two u16 gains in tenths, u32 `hold_ms`, u32 `wait_ms`, four trackball target bytes and four paddle target bytes, each in U/D/L/R order, followed by u16 rolling gain in tenths of a degree per raw point, u8 paddle mode and u8 rolling flags. Gain accepts 1–100 (default 10), mode 0 is Button clicks (default) and 1 is Virtual Rolling, and flags use bit 0 for reverse and bit 1 for Left stick (zero defaults to Right stick). Other flag bits are rejected. Appended u8 trackball_mode is 0 for legacy Virtual Rolling or 1 for Hold; u8 trackball_hold_threshold accepts 1–127 with default 1. The following u8 rolling_step_deg uses one former padding byte and accepts only 5, 10, 15, 20, 30, 40, 45, 60 or 90 (default 30). The last alignment byte is not serialized; the structure remains 32 bytes. Field-wise equality ignores padding. These settings are device-wide. Initial numeric values are 64/60/15/30/20. The device retains zero as the backward-compatible encoding of the original direction; the GUI displays explicit ↑/↓/←/→ defaults and saves their selected output IDs. A target byte of 0 uses the original direction. Values 1–18 are profile output ID + 1: Y, B, A, X, L, R, ZL, ZR, Minus, Plus, L3, R3, HOME, CAPTURE, Up, Right, Down, Left. Storage validation accepts threshold 1–65,535, ball 10–2,560 and paddle 10–100 tenths, and each duration 1–1,000 ms. Readback retains those ranges for compatibility. Editing through command 53 accepts threshold 1–256 and each duration 1–512 ms; it preserves both hidden cursor gains. `upr_set_direction_settings` loads this structure at boot and after a successful settings save. The normal `um_mix` path uses the profile’s original 8-byte mouse options and no longer masks pointer movement when a conversion bit is set. `upr_pointing_input` returns the pointer deltas and independent direction events from the same received report. `up_mapper_apply` provides a neutral/current gamepad state even when no digital binding was touched; generated clicks then overlay the selected button bit or hat value after normal button routing. No D-pad-assignment bit is checked. Both combined button behaviors carry these generated clicks. Crossing either signed limit appends one event and zeroes only that axis, discarding all excess. The device-wide persisted threshold is initialized to 64. Output order is ball X, ball Y, paddle; paddle X emits left/right and paddle Y emits up/down, both retaining paddle inversion. The 7-byte `um_key_events` carries a count, three directions and three source bytes (0 trackball, 1 paddle). Both trackball axes select the trackball mapping; the paddle selects its own mapping after axis and inversion processing. `upr_pointing_input` extracts each relative report once for both mouse and direction routing. Readiness loss and profile resets clear the sums.

`ub_direction_pulse` remains a 76-byte state machine with four waiting clicks. Each pending event retains its direction and source, and the active state retains that source through press/release ACKs. The source bytes use existing padding, so the queue allocation does not grow. Output and physical-conflict checks use the selected source map, including when equal directions from different sources are queued consecutively. It overlays only the selected generated button bit or hat value onto normal output, preserving unrelated button/axis transitions and independent mouse scheduling. The held direction level still identifies the source U/D/L/R direction for ACK accounting and the keyboard diagnostic. States are idle, waiting for press ACK, held, waiting for release ACK, and released gap. The held and gap timers begin only at the matching successful completion callback, and use unsigned elapsed-time subtraction across clock wrap. The held phase uses saved `direction_settings.hold_ms * 1000`, while the gap uses saved `direction_settings.wait_ms * 1000`; their initial values are 30,000 and 20,000 us respectively. `ub_direction_prepare` receives them as independent arguments. Its guard requires both to be 1,000–1,000,000 us and clears pending output if either is invalid. An edge is counted once; failures remain retryable. Reset clears pending state and invalidates old completion cookies. A physical report holding the selected button, or any physical hat when the target is a direction, takes priority. New conflicting clicks are rejected; a conflict with the current/next generated target resets pending generated work and invalidates its ACK cookie. The unmodified physical report is retained, so no generated release can release a held physical button. Physical hat input can coexist with a generated face/menu button. Capacity overflow discards a whole new click and increments the direction drop count. Ordinary physical-state queue overflow remains independent. `ub_frame` stays 20 bytes: its former padding holds both the one-time ACK edge marker and the held direction level. The UDLR encoder uses the level on repeated reports, so normal 1 ms polling cannot release a held key early. The older pair helper remains available to its packet-format tests but is not used by the application scheduler.

Read-only Feature command **49** returns 56-byte `DKY1`: schema byte 4=1; byte 5=active conversion; bytes 6–7 reserved zero in normal firmware. Offset 8 is threshold (u32); 12/16/20 are ball-X, ball-Y and paddle signed sums in tenths (i32); 24 generated clicks, 28 enqueued clicks, 32 acknowledged presses, 36 acknowledged releases, 40 full-queue drops, 44 physical-target conflicts, 48 ordinary queued frames plus unfinished generated direction edges, 52 ordinary queue-overflow resets (all u32). Counters are modulo 2^32. The diagnostic remains read-only; commands 52/53 provide the separate settings interface.

Read-only command **51** returns `DPT1`, schema byte 4=1, phase byte 5 (0 idle, 1 press ACK pending, 2 held, 3 release ACK pending, 4 gap), last/current direction byte 6 (1 U, 2 D, 3 L, 4 R; phase determines whether it is held), queued-click byte 7. Remaining fields are u32: offset 8 minimum press us; 12 minimum release us; 16 waiting capacity; 20 measured press count; 24/28 minimum/maximum ACK-to-ACK pressed duration; 32 measured consecutive released-gap count; 36/40 minimum/maximum ACK-to-ACK gap duration; 44 unfinished direction edges; 48 last edge ACK time; 52 source receive time. Offsets 8 and 12 return the actual saved hold and wait durations respectively, converted to microseconds and initially 30,000 and 20,000 respectively; the DPT1 schema and offsets remain unchanged. Zero samples means no measured range. Idle gaps are excluded from consecutive-gap statistics. Timing statistics remain across output resets, while active/pending work is cleared. The CLI reads this using `python tools/controllerctl.py direction-timing`. These statistics do not demonstrate application-level reception on another host.

The ordinary gamepad descriptor uses Generic Desktop Hat Switch (usage 0x01/0x39), with up/right/down/left values 0/2/4/6 and null value 15. This matches the existing physical-direction mapper. The separate keyboard test maps U/D/L/R to page-7 usages 0x18/0x07/0x0F/0x15 with Shift, not arrow key usages. See [USB-IF HID Usage Tables 1.7](https://www.usb.org/sites/default/files/hut1_7.pdf) for the usage definitions; the initial 30/20 ms intervals are an implementation choice, not a USB or Nintendo requirement.

## Trackball Hold runtime (0.20.16)

Hold requires a ready active profile with relative trackball X/Y, Trackball enabled, its conversion bit set and device-wide trackball_mode=1. `um_hold_state` is 8 bytes (last valid report time and a four-bit U/D/L/R mask plus padding); the cached idle deadline is a further 4 bytes. `um_hold_input` applies profile X/Y inversion with signed 64-bit intermediates, then compares each raw magnitude to the dedicated threshold. It does not apply either gain or accumulate movement. Zero/subthreshold values clear their axis, sign reversal selects the other direction when eligible, and X/Y can coexist. `um_direction_keys` suppresses only the trackball clicks in this mode and clears their sums; paddle and pointer processing continue.

Only a valid trackball report updates this state. A paddle-only report, wrong interface/report ID, or malformed/truncated report cannot synthesize zero. The no-report fallback is max(20 ms, twice the effective trackball input polling interval), using the profile override or cached descriptor endpoint interval. This clock-wrap-safe check is gated by Hold mode. Resets/readiness loss clear Hold. Successful settings saves clear current and queued Hold masks while preserving ordinary physical input state.

`ub_frame` remains **20 bytes**: `hold_directions` uses its last padding byte. Queue change detection includes this mask, preserving rapid press/reverse/release transitions before USB ACK. Input, rapid-fire and measurement frames carry it. The scheduler uses the queued mask for queued frames, otherwise the current runtime state for idle expiry. `um_hold_overlay` runs after ordinary mapping and before generated paddle clicks; mapped buttons are ORed, opposing generated hat directions cancel, and any physical hat owns the hat. Axes are unchanged. A conflicting paddle click follows existing generated-click conflict handling. Paddle Virtual Rolling overlays its selected stick afterward. Repeated reports are cancelled when the complete report, Hold mask or pulse fields change, so a stale repeat cannot retain a released Hold.

The UDLR diagnostic encodes all active U/D/L/R bits as shifted letters and merges any active paddle click. It can therefore hold both letters of a diagonal. Commands 49/51 and the existing log counters still describe **clicks**, not Hold duration or a complete Hold history; PC keyboard autorepeat can add repeated characters while one key is held.

## Virtual Rolling runtime (0.20.16)

Virtual Rolling requires an active matching profile with a relative wheel input, Paddle enabled, its conversion bit set, and device-wide paddle mode 1. `um_rolling_state` remains **12 bytes**: last-motion timestamp, angle in tenths of a degree, signed residual tenths, cached X/Y, moving state and a cached step in a former padding byte. Startup zero means up. A **38-byte, 19-entry uint16 Q15 quarter-sine table** covers 0° through 90° in 5° increments, with quadrant reflection for all reachable angles. Positive/negative stick extents use 127/128 with nearest-integer rounding; the default 30° vectors remain byte-identical. No floating-point or trigonometric work runs per input.

For each nonzero valid wheel report, signed movement is `-wheel * rolling_gain10`, optionally reversed by the dedicated flag, using 64-bit intermediates. Valid steps are the nine multiples of 5 from 5 through 90 that divide 360. If the cached step differs, first round the retained angle to the nearest new step measured from up (`((degrees + step/2) / step * step) % 360`, clockwise on ties), clear the old residual, and cache the new step. Add the residual to the movement, divide by `step * 10` with truncation toward zero, retain the signed remainder, and advance the angle by whole steps modulo 360°. Multiple steps and full turns require no loop per detent; the latest position is output. 90° therefore always yields the four cardinal vectors, including after a step change. Pointer gains, pointer inversion and paddle X/Y selection do not affect this calculation. Trackball clicks and both pointer sources remain independent; paddle clicks are suppressed in Virtual Rolling mode.

A real zero-wheel report clears moving state only. Reports for another interface/report ID, or invalid/truncated reports, do not synthesize a stop. Without a new paddle report, `um_rolling_overlay` stops motion after max(20 ms, twice the input polling interval). The interval uses the profile override when nonzero, otherwise the wheel interface's cached endpoint descriptor. Elapsed-time comparison handles the 32-bit clock wrap. Input/output resets and settings saves stop movement but preserve both angle and residual; only `upr_init` resets them unconditionally. A changed step performs the alignment/residual reset above on the next nonzero report. Other setting changes leave them intact. No game-state signal is read and no angle is persisted.

The normal send scheduler overlays the selected stick after ordinary mapping, combined-output routing and generated button pulses, on both new and repeated reports. Moving outputs the lookup vector; idle outputs center. The chosen stick belongs to this mode while enabled; other axes/buttons remain unchanged. The ordinary queue never stores the virtual vector. Changes to the full report, Hold mask or pulse identity cancel stale ordinary repeats so a stop can reach USB without waiting for another physical report. The optional keyboard-only UDLR build has no stick report: select Button clicks to test paddle letters.

## Device-wide direction settings and test-build separation (0.20.16)

Common configuration slot 0 remains at Flash offset `0x1FE000` (4 KiB). Its original 16-byte `CBST` header, 40-byte payload, length and CRC are unchanged. Offset 64 retains the 16-byte `DKC1` record: magic, u32 schema=1, u32 threshold and CRC32 over the first 12 bytes. Offset 80 retains the 16-byte `DKG1` record: magic, u32 schema=1, u16 ball gain, u16 paddle gain (tenths), and CRC32 over the first 12 bytes. Offset **96** retains `DHT1`: u32 magic `0x31544844`, u32 schema=1, u32 hold milliseconds and CRC32 over the first 12 bytes. Offset **112** retains `DWT1`: u32 magic `0x31545744`, u32 schema=1, u32 wait milliseconds and CRC32 over the first 12 bytes. Offset **128** retains `DMP1`: u32 magic `0x31504d44`, u32 schema=1, four trackball U/D/L/R target bytes and CRC32 over the first 12 bytes. Its previous shared assignments become the trackball map. Offset **144** adds the 16-byte `DPM1` record: u32 magic `0x314d5044`, u32 schema=1, four paddle U/D/L/R target bytes and CRC32 over the first 12 bytes. Offset **160** adds the 16-byte `VRS1` record: u32 magic `0x31535256`, u32 schema=1, packed rolling options and CRC32 over the first 12 bytes. The packed u32 is gain in bits 0–15, mode in 16–23, and flags in 24–31. This VRS1 encoding remains unchanged and differs from the UDS7 wire options below. Offset **176** adds the 16-byte `TBH1` record: u32 magic `0x31484254`, u32 schema=1, u32 Hold options (threshold in bits 0–7, trackball mode in bits 8–15, upper 16 bits zero), then CRC32 over the first 12 bytes. Default options are `0x00000001`; Hold with threshold 1 is `0x00000101`. Offset **192** adds the 16-byte `RSD1` record: u32 magic `0x31445352`, u32 schema=1, u32 step in degrees (one of the nine valid choices), then CRC32 over the first 12 bytes. VRS1 and TBH1 keep their existing encodings. `ub_store_save_configuration` assembles all nine records in the existing buffer and performs one sector erase/program. The records total 144 bytes. The sector uses **208 bytes** including alignment, leaving **3,888**. The earlier 192-byte prefix is preserved during migration; profile banks and measurements are unchanged.

The loader validates threshold, gains, hold, wait and target mappings independently. Missing/invalid DHT1 initializes only hold_ms to 30 while preserving valid threshold and gains. Missing/invalid DWT1 inherits hold_ms only when DHT1 supplied a valid saved hold value, preserving the previous shared-duration behavior. Otherwise wait_ms retains its independent 20 ms default; valid saved wait_ms is never replaced by that fallback. Missing/invalid DMP1 initializes only the trackball assignments to zero, preserving every valid older threshold/gain/timing value. Missing/invalid DPM1 copies the loaded trackball map to the paddle, preserving the old shared behavior. A valid paddle map is retained even if DMP1 is invalid. Missing/invalid VRS1 defaults only the rolling options to Button clicks, gain 1.0°/pt, Right stick and no reversal. Missing/invalid TBH1 defaults only the trackball mode to Virtual Rolling and its Hold threshold to 1, preserving valid paddle options and earlier values. Missing/invalid RSD1 defaults only rolling_step_deg to 30, preserving all other valid settings. Reading storage does not write it. Each remaining invalid record falls back independently. Missing/invalid records are saved once before USB starts, sharing a pending boot-capture consumption write. Valid saved values survive later boots without being overwritten by defaults. Firmware 0.20.15 ignores RSD1 and erases it on a common-settings save; a later 0.20.16 boot restores the default 30° step. Firmware 0.20.14 ignores TBH1 and erases it on a common-settings save; a later 0.20.15 boot restores Trackball Virtual Rolling and Hold threshold 1. Firmware 0.20.13 ignores VRS1 and erases it on a common-settings save; a later 0.20.14 boot restores default Button clicks mode. Firmware 0.20.12 ignores DPM1 and erases it on a common-settings save; the next 0.20.13 boot copies its then-current shared mapping to both sources. Firmware 0.20.11 ignores DMP1 and DPM1 and erases them on a common-settings save; a later current-version boot restores original-direction targets for both sources. Firmware 0.20.9 ignores DWT1, but a common-settings save with that version erases it; a later 0.20.10 boot recreates wait_ms from the then-current hold_ms. Firmware 0.20.7 similarly ignores DHT1 and later records but erases them on a common-settings save; firmware 0.20.4 retains only DKC1. A failed save is reported as not persisted.

Command 2 retains its 40-byte prefix and appends `DKC1` at 40, actual threshold u32 at 44, actual hidden ball/paddle gains in tenths (u16 at 48/50), schema byte **2** at 52 and persisted flag at 53. The flag covers all nine direction/mode records; command-2 schema 2 and its fields remain compatible. The 56-byte response layout is unchanged; command 51 provides the hold and wait values. Commands 3/4 retain the old input layout and preserve all cursor settings. Commands 52/53 expose click threshold, hold/wait durations, target assignments and both source modes/parameters through the Mouse UDLR settings dialog. Cursor gains have no GUI setter. Profile 848 bytes, bank 13,908 bytes and measurement 3,784 bytes are unchanged. UDLR logs read actual hidden gains through command 2; they are not hard-coded constants.

### Shared settings commands and dialog

Both normal and test firmware expose commands **52** (read) and **53** (save). Capability bits 18/19/20 identify shared settings, target assignments and independent source maps; bit 21 adds paddle Virtual Rolling, bit 22 adds Trackball Hold, and bit 23 adds configurable rotation steps and the current schema. Both return a 56-byte payload: `UDS7` at offset 0, u32 schema 7 at 4, u32 click threshold at 8, u32 hold milliseconds at 12, u32 wait milliseconds at 16, u32 persisted flag (0/1) at 20, four trackball U/D/L/R target bytes at 24–27, four paddle targets at 28–31 and packed mode options at 32–35. Remaining bytes are zero. All integers are little endian. Older UDS1/UDS2/UDS3/UDS4/UDS5/UDS6 writes are rejected; the configurator requires matching firmware and validates schema, targets and both mode groups.

The packed **UDS7 mode options** use byte 0 for paddle rolling gain (1–100 tenths), byte 1 bits 0/1/2/3 for paddle Virtual Rolling / reverse / Left stick / trackball Hold, byte 2 for Hold threshold (1–127), and byte 3 for rotation step in degrees (5/10/15/20/30/40/45/60/90). Byte 1 bits 4–7 are reserved; mask `0x0000f000` must be zero. Default packed options are `0x1e01000a`. The step participates in range validation, stale-edit comparison and readback equality. These wire options use `udk_modes_pack/unpack`; Flash VRS1 retains `udk_rolling_pack/unpack`, and TBH1 uses `udk_hold_pack/unpack`.

Command 53 accepts a 56-byte payload: `UDS7` at 0, schema 7 at 4, expected old threshold/hold/wait at 8/12/16, desired threshold/hold/wait at 20/24/28, expected old trackball targets at 32–35, desired trackball targets at 36–39, expected old paddle targets at 40–43 and desired paddle targets at 44–47, expected old packed mode options at 48–51 and desired mode options at 52–55. New numeric values must be 1–256 pt and 1–512 ms for each duration; target bytes must be 0–18; packed mode options must satisfy the gain, Hold threshold, rotation-step and reserved-bit validation above. Invalid magic/schema/ranges return status 1. A stale expected numeric value, source target or packed mode option returns status 4 unless all desired settings already match, permitting a retry after a lost reply. Busy measurement/output reconnection returns status 2. The shared `udk_settings_request` codec prepares a candidate without modifying the live settings. The firmware preserves hidden gains, persists the candidate in one common-sector write, then applies it. Storage failure returns status 3 without applying the candidate. Already-persisted equal values require no Flash write. Success resets click sums/pending work, clears current/queued Hold masks and stops rolling motion, retaining the virtual angle/residual, ordinary pointer/button queues, profiles and USB mode.

The header button is immediately right of Profile switching, before the test-only UDLR button when present. The modal dialog reads current values on open, supports three shared integer fields with adjacent units and separate Trackball/Paddle tabs, with four click-target lists in a D-pad arrangement and Reset to defaults in the center. The Trackball tab selects Virtual Rolling (legacy clicks) or Hold, retaining its four assignments in either mode. Hold shows its own integer Movement threshold (default 1, range 1–127) with adjacent pt and no range annotation, while keeping the three shared click fields visible and disabled without losing their drafts. The Hold threshold row remains visible and disabled in trackball click mode. The Paddle tab selects Button clicks or Virtual Rolling, whose pane contains sensitivity (one decimal place), a DropDownList for the nine integer rotation steps with an adjacent ° unit, output stick and reversal controls. The step loads the saved value, defaults to 30, and cannot accept arbitrary text. The header action and client require the rotation-step capability and matching 0.20.16 firmware. Both paddle direction and rolling parameter groups remain visible; only the active group is enabled. The common click fields are enabled only when the currently selected source tab uses its click mode. `UpdateModeControls` is the sole enabled-state path, called after all controls and the initial Trackball tab are constructed, on either mode/tab change, and when saving starts or finishes. It updates group Enabled states and the save/cancel controls; it never toggles mode-group visibility or row heights. The dialog reserves a 560×840 logical client area and a fixed 470-pixel tab row at 96 DPI, scaled by the normal form layout. The paddle direction grid and rolling options occupy separate rows rather than overlapping in one cell. Local label/check-box painting uses readable grey for disabled text in the dark theme. The dialog saves through command 53 followed by an independent command-52 readback. The list contains exactly 18 Switch digital outputs: four directions and 14 buttons, including both stick clicks but excluding analog axes and Unassigned. Its item objects retain encoded output IDs independently of display order. GUI defaults and reset use explicit U/D/L/R bytes 15/17/18/16. Opening an older zero mapping selects the corresponding direction while retaining the raw original bytes for the command-53 stale-edit guard. Tab switching retains both drafts. Reset changes only the displayed tab, retaining the other source and numeric settings; it requires Save to device to persist. It closes only after the numeric values, all eight source assignments, both packed mode groups and persisted flag match. In-flight saves disable both tabs, all controls and closing; failures retain inputs for retry. Cancel does not write. Polling pauses around the modal operation and resumes afterward without reloading or discarding unsaved profile drafts. Readback accepts earlier storage ranges; out-of-edit-range values are shown clamped with an explicit notice and are changed only by a confirmed Save to device. The current common-settings layout uses 208 bytes; no profile/bank/JSON version changes are required.

The normal build excludes `udlr_test.h`, keyboard output, test gate/heartbeat, command 50, `UdlrTestDialog`, its command-line check entry, and its header button.
